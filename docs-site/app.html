The OceanVal app

View, analyse or validate a simulation from a browser window, with no Python.

The OceanVal app lets you validate a simulation without writing any Python. Run oceanval in a terminal and a page opens in your web browser that takes you from a folder of model output to a validation report: you choose what to do, point it at your simulation, choose the observations to validate against, check the units, and watch the run. The first page offers four boxes, two by two: View simulation output, Analyze simulations, Compare simulations and Validate simulations. View simulation output maps what the files hold (see below), Validate simulations leads to the validation choices, and Analyze looks at a simulation on its own (see below).

Start it

oceanval only runs from a conda environment that has OceanVal installed (see Installing), as it needs the R packages, cdo and nco that conda provides. In a terminal, activate that environment, then run oceanval in the directory to work in:

bash 
conda activate foo
oceanval

Replace foo with the name of your own environment. If the command is not found, the environment is not active, or OceanVal is not installed in it. OceanVal and python -m oceanval do the same. Matchups, scripts and reports are written in that directory unless you choose another, so make a new directory for each simulation.

What to match up is chosen on two pages, each opening with an Explainer box of what the tags beside the datasets mean (the domain a dataset covers, clim for a climatology and TS for a gridded dataset covering multiple years, Vertical for the tick box of variables with 3D data, which is ticked to validate them in 3D, then the name of the data source), each with a Deselect all button in its datasets column, and each turning a variable’s row light teal once a dataset in it is ticked. Select gridded datasets to compare with observations comes first: for each variable, the simulation variable and the gridded datasets to validate it against, with an i beside each of OceanVal’s sources that gives the years its observations cover and a link to its web page (NSBC, for example, is a climatology of 1960–2014). Each gridded dataset ticked needs the years of the simulation to validate it with, its From and To, which are required. What simulation years do you want to use to compare with climatologies?, at the top, fills them in for every climatology ticked, in red and bold, and any of them can still be changed; WOA23 temperature and salinity are published per decade, so their years must sit inside one, and are marked in red until they do. Continue goes to Select point datasets to compare with the simulation, with Back to return: for each variable, the point datasets, and a last column saying which gridded datasets were chosen for it. Settings for all point matchups, which asks What simulation years do you want to compare with point observations?, and Match point observations by, at the top, are filled in for every point dataset ticked, where each can be changed for one dataset; the years are required when a point dataset is ticked. Matchup is given every year any dataset is validated for.

Where the matchups (and the report) are saved, and what the matchup script is called (matchup.py, or matchup1.py, matchup2.py and so on if that file is there already), are asked once you have chosen what to match up, checked the units, and said you are happy with the files OceanVal found: the page Where do you want the matchups to be saved?, whose button is Continue. Nothing is written in that directory before then. If the directory you choose has matchups already, from an earlier run, the page lists them, each with its variable, source and whether it is point or gridded, and asks What do you want to do with existing matchups? What you can do with each depends on what this run matches up. Replace is offered for one this run matches up, and makes it again; it is chosen to start with. Use keeps it as it is, without making it again, and validates it, and is chosen to start with for one this run does not match up. Ignore is offered for one this run does not match up, and leaves it out of the report; without a report, those are left as they are and not listed. Ticking an option at the top of its column chooses it for every row that has it. Nothing is removed from the directory. You must tick to confirm what is done with them before carrying on. The last page, One last thing... How would you like your validation report?, asks for the report’s options and how many cores matchup should use, which has no default, followed by what to treat as missing values (for a simulation that looks like NEMO-ERSEM, zeros are assumed, marked as such). Its spatial subset is matchup’s: only simulation output and observations inside it are matched up, so the report covers no more. With Match up only, which builds no report, the cores, the missing values and the spatial subset are asked on the page of where the matchups are saved, whose button is then Match up. See Matchups from earlier runs.

Beside it is Do you want to mask part of the domain?, which starts on No. With Yes, give a netCDF file with a single variable and a single time step: 1 in the cells you want, 0 or missing elsewhere. The file is checked as you type its path, and drawn, with how many cells will be matched up; the simulation is regridded to the file’s grid by nearest neighbour, and only the cells (and point locations) of 1 are matched up. It is kept as oceanval_matchups/domain_mask.nc, and the matchup script saved names your file, as matchup(..., domain_mask=...).

If you have observations of your own, the Your point data and Your gridded data steps add them one dataset at a time. OceanVal reads the simulation’s variables in the background as soon as the simulation step is answered, so clicking in Simulation variable opens the list of the variables with their long_name, searched by what you type in the box, where clicking a variable ticks it and ticking several sums them (a+b); a name that is not in the output is refused. For gridded data on your machine, typing the path of a netCDF file, a directory of them or a pattern fills the Observation variable list with the variables in the first file. Data on a server is not looked at, and either box can still be typed in.

Once you have given the directory a simulation’s output is in and how many directories down its files are (type a number, or pick 0 to 5 from the list the arrow in the box opens; if you leave it empty, OceanVal fills it in, in amber, when it recognises the folders: YYYY/MM/**.nc is 2, MM/*.nc (the months 01 to 12) is 1 and files with no subdirectories is 0, and typing a number of your own replaces it), OceanVal reads the years the output covers from the times in its files, never from their names, while you fill in the rest. It takes a few seconds however many files there are: OceanVal reads the time axis of the first and last files of each kind of output, by name and by when they were written, and of some others chosen at random as a check, and reads every file of a kind only if the check finds one out of order. Only the simulation’s main output counts: the kinds of file with at least a tenth as many files as the most numerous kind, and at least two, unless every kind is a single file. Files beside it, such as a post-processed time series or the grids an earlier validation saved, are left out. While it does, the page says Finding key information about your simulation, and Found output for the years once they are read. The Skip file names containing box starts empty for Validate, Analyze and each simulation of Compare, so restart files, for example, are used unless you type restart in it; OceanVal never leaves a file out that you have not asked it to. In the recipes window, the years to validate and the years for climatologies then have an arrow at their right-hand end that lists those years. Any year can still be typed, in case the years found are wrong; years partly outside them are warned about, on the dataset and in the years boxes, but allowed, and years with none of them in the output are refused, as nothing could be matched up. The years are remembered in .oceanvalcache in your home directory, and read again only when the files change.

While the files are found the page says Identifying files that meet criteria. Please wait! Once you choose Match up and validate, it shows a grid with a row for each variable and data source. The Matchup column is empty until that matchup starts, has a turning circle while it is made, and a tick once it is (a cross if it could not be). Model extraction, the first column before it, shows how many of the simulation’s files that matchup has read so far, such as 37/120, and a tick once it has read them all. A dash means it read none, for example because it was kept from an earlier run. For gridded data the files are read by CDO, and OceanVal counts each one as CDO finishes with it. It checks twice a second, so a file read in less time than that may only be counted once all of them have been read. Observation extraction, the column just before Matchup, has a turning circle while the observations are read or downloaded (from a server, the data store or your own files), and a tick once they are, or a cross if the matchup could not be made while reading them. A point matchup reads its observations before the model files, a gridded matchup after them. In a narrow window both extraction columns are left out and the count appears under the Matchup circle. The Interim report column does the same as its page is added to the interim validation report, and its tick opens that page; the link to the whole interim report is at the top. The Time column counts up while a matchup is made, and keeps how long it took once it is made (or not made), and Time elapsed under the grid is how long the run has gone on for, the report included. OceanVal’s output is shown only if the run fails, with its errors. If a data server is down or overloaded (NOAA’s for WOA23, say, answering 503 Service Unavailable), a notice at the bottom of the window says so as soon as a matchup fails because of it: which server, what it answered and when, and the matchups it stopped. This is a problem at the server’s end, not with your simulation, so try those matchups again later. The notice stays until the next run, and the × hides it until there is more to say.

Demo

Viewing a simulation’s output

View simulation output lets you look at what a simulation’s netCDF files hold, and map any variable in them at the time, depth and years you choose. Nothing is written but a record of the files’ times (below), and only the map on show is ever read from the files: one time step at one depth of one file, so output of many GB stays quick to look at.

  1. The simulation: the same page as for Analyze and Validate, with the directory, how many directories down the files are (filled in, in amber, when OceanVal recognises the folders, as above), the file filters, with Skip file names containing starting empty, and the arrow in the directory box listing the simulations used before (one you have viewed is added to it). Below them, Missing values (optional): numbers in the files that mean there is no data, such as 0 or -999, and are not marked as missing in them. Give one number, or fill in To as well for a range (both ends are included). Once the files are found, OceanVal says it is attempting to identify the missing value range: it looks for a value that the same cells have in every file (such as 0 or 1e+20 on land) and, for a NEMO-ERSEM simulation, otherwise assumes 0. What it finds is filled in, in amber (ERSEM's own colour for the assumed 0), for you to check; once you type in the boxes, OceanVal leaves them alone. They apply to every variable, and cells with them are left blank and do not stretch the colour scale. Back from the viewer returns here to change them, with everything as you left it.
  2. Continue reads the variables of the first file of each file type (the files whose names differ only in their dates, so ..._20000101_grid_T.nc and ..._20000201_grid_T.nc are one type) and opens the viewer straight away. The times of all the files are then read in the background while you use it (only the time variable of each file, in a process of its own using half of the machine’s cores), with a count such as Reading the times of the files: 1,240/3,560. Until they are in you can map the first time of any variable, but not choose the years or move through time. The times are kept in .oceanvaltimes in your home directory, so a simulation opened again has its times at once and only new or changed files are read.
  3. The viewer. On the left, search the variables by name, description or units (* stands for any characters and ? for one, so P*_Chl finds P1_Chl and P2_Chl); only those that can be mapped (with two horizontal dimensions, or on an FVCOM mesh) are listed. Clicking a variable maps it; if it is in more than one file type, choose which. To map the sum of several variables, tick their boxes (or press Shift+Enter on the highlighted one); Clear unticks them all. They must be in the same file type with the same dimensions, so a variable that cannot be added is dimmed. Your missing values are applied to each before they are added, and a cell missing in any of them is missing in the sum; if their units differ the sum is still drawn, so check they make sense added. Below are what the variable is (its units, dimensions, file type, files, time resolution and dates) and the controls:
    • Years: a First year and a Last year, typed or picked from the list the arrow in each box opens; a blank box is no limit. Time, Play and its colour scale then stay inside those years, and the details say how many of the files hold them (“Files 120 of 444”). A first year after the last, or years with no output, are said and not used; a year beyond the output is only mentioned.
    • Time: a slider, the arrow buttons (or the arrow keys), and Play, which animates the simulation from the time shown at Slow, Normal or Fast (2, 5 or 10 frames a second, as fast as the files can be read), on one colour scale for the whole run, keeping your zoom.
    • Depth: the level to show (for FVCOM, its sigma layers, Layer 1 being the surface).
    • Colours: the colour map, fixed limits (Keep this scale for every time, Automatic scale), a logarithmic scale and Coastlines.
    On the right is the map, which you can zoom, pan, hover over to read values, and save as a PNG. It keeps the area’s true proportions, distances east–west and north–south on one scale (a degree of longitude being narrower than one of latitude away from the equator), as large as fits: it fills the width or the height of the space, centred in the other, and is fitted again when the window is resized. A map drawn by the grid’s indices fills the space. As in ncplot, a regular longitude/latitude grid is drawn as an image, an uneven or curvilinear one as a quadmesh, and a grid whose longitudes and latitudes cannot place every cell (land cells written as 0, say) by its own indices. When the values span 0 the colour scale is symmetric about 0, in RdBu_r; otherwise it is viridis. Raw FVCOM output is drawn as pyfvcom2 draws it, a value on the nodes shaded across each triangle and one on the elements filling it, onto a grid of about 1000 pixels across; its coastline is Natural Earth’s, which cartopy downloads the first time.

Analyzing a simulation

Analyze simulations works out the climatology, the phenology, time series and transects of a simulation’s variables, with no observations, and builds an HTML report of them, laid out like a validation report. It takes you through these pages, each with Back, which keeps what you entered:

  1. Simulation: where the model output is, as for a validation, but with no domain to choose. Where the analysis is saved is asked last, on the final page.
  2. Choose the variables to analyze. A row for each variable, with Environmental variable for it and the Variable name in the simulation holding it, in one box: clicking in it opens the list of the model’s variables with their long_name, and what you type searches it (after a +, the search starts again for the next variable). Clicking a variable ticks it and adds it, and ticking several sums them (P1_Chl+P2_Chl); names typed in the box are ticked. The arrow at the right-hand end of Environmental variable lists the names OceanVal knows from validation (Temperature, Salinity, Chlorophyll and so on): choosing one fills in the Variable name in the simulation as the matchups would find it (shown in red and bold until you change it), if your model has a variable for it. Nothing else is filled in for you: the rows start empty.
  3. The files holding each variable, their time resolution and their dates. OceanVal reads the date of every file and says whether any are missing; Show the months shows which. If the model’s time means look dated at the end of the period each covers, the page first asks whether to shift every time back a day.
  4. The analyses. Under Select one or more of the analyses, six boxes, Map climatologies, Map phenologies, Long-term time series, Seasonal cycles, Map temporal changes and Analyse transects, each opening a large pop-out with a row for each variable, and Cancel and Confirm at the bottom. Each variable has a tick by its name, unticked to start with: tick it to include the variable in that analysis (ticking one of its layers ticks it too). Confirm stays greyed out until at least one variable is ticked. What has to be given is marked Required, in red: each ticked variable needs its years and Surface, Bottom, Water column or more than one, or it is said by its row. With more than one variable, the table starts with an All variables row: what is set there (the tick, the years, the layers and the other options) is set for every variable it applies to (the bottom is not set for a variable with no depth levels, for example). Each variable can still be set on its own afterwards, and one set otherwise than the All variables row has Reset to All variables under its name to put it back. An i beside an option says what it plots: click it, beside Surface, Bottom and Water column (in each variable’s row and in the All variables row), beside the title of the phenology pop-out, and beside the Climatology and Changes of the Surface and the Vertical part of each transect, and a pop-out gives the words. Nothing is drawn: the pop-out says in words what the option will plot and how it is worked out. Once an analysis has been confirmed, a Remove this analysis button appears in its pop-out to leave it out again. The climatology is the mean of each month of the year, and the annual mean, over the years from Start to End, at the Surface, at the Bottom (the deepest value that is not missing) and/or through the Water column, as its vertical mean or its depth integral, which needs the cell thickness (the name of its variable, a file, or z_level). The phenology is the day of the seasonal peak at the surface, from a daily climatology, so it is offered only for daily output: if no variable has daily output, opening Map phenologies shows a No daily output pop-out instead, which says so for each variable and has a Close button that returns to the options page. The two time series are the mean of each year, and of each month, over the model’s domain, each region you choose and each station (a name, longitude and latitude, in a table in their pop-outs; the nearest model cell is used). Once one is chosen, a card sets the regions and area they share: no regional summaries, the northwest European Shelf, global, or your own .nc file, and a lon/lat box. Map temporal changes maps how a variable changes between a historical period and one or two future periods: for each variable ticked, give the first and last years of the Historical period and of Future 1 (both required) and, if you like, Future 2, tick Surface, Bottom and/or Water column as for the climatology, and choose, in a row below, Plot (Historical + Future (absolute values), Historical + Future (absolute values) + Changes or Historical + Changes) and Change (absolute or percentage); neither is chosen to start with. Transects are the model’s values along straight lines: tick each variable you want transects of, and you add as many transects as you like to each, on its own. With more than one variable, each has a Copy these transects to every variable button, which gives every other variable the same transects in place of its own (a variable with no depth levels gets them without the Vertical part). A transect is a card with the longitude and latitude of its Start and End (it must run north–south, with the same longitude at both ends, or east–west, with the same latitude) in one line, and, below them, a Surface and a Vertical part, each with a Climatology (at the surface, the monthly climatology along the line; in the vertical, a section of the annual mean through the water column, which asks whether the simulation is z-level or where its cell thickness is) and its Changes, a drop-down of Absolute (the linear trend per year), Absolute change (the last year minus the first) and Percentage change, at the surface or at each depth of the section, which are not offered for a variable with only one year of output (the absolute trend needs three). Each has its own required Start year and End year, and a Use a rolling mean (years) box to the right of those of the changes, 1 to start with (none), smooths the annual means with nctoolkit’s rolling_mean before the trend is worked out. Nothing is ticked or filled in to start with, and each variable’s years of output are shown beside it as a hint. Every start and end year box also has an arrow at its right-hand end (or press the down arrow in the box) that lists all the years of that variable’s output to pick from; a year can still be typed. The Long-term time series pop-out has two more columns after Water column: Use a rolling mean (years), 1 to start with (none), which replaces each year’s annual mean by the mean of that year and the ones before it, and Show as: Absolute value (the annual means, to start with), Absolute change or Percentage change, each year’s change from the first year with a value.
  5. Cores, missing values and figure code. Continue, which stays greyed out until at least one analysis is chosen, goes to a second page, with Back to return to the boxes (what you chose is kept). There you must say how many cores OceanVal may use, which has no default, and what to treat as missing values; OceanVal looks at the surface of the first variable at the first time step of up to ten of its files, and if a value is the same in a good many cells of every file (as land is) it fills it in, in amber, and asks you to check it; otherwise, as for validation, a NEMO-ERSEM simulation is recognised and zeros are assumed, marked as such. Anything you type is kept. You must also answer Do you want the report to contain code to reproduce figures?, Yes or No, with neither chosen to start with: with Yes, each figure in the report has a Copy code to reproduce figure button at its top right, which copies the Python code that draws it from the analysis’s saved results, to change and run in the conda environment OceanVal ran in.
  6. Choose where to save the analysis. The last page, reached with Continue once the cores and the figure code are answered, with Back to return to them. The analysis is saved in a folder called oceanval_analysis in the Directory you choose, replacing any analysis there. If there is one, the page says so and you must tick to replace it, and name the directory in the box rather than leave it empty (empty is the directory you started oceanval in); choose another directory to keep the analysis. Also give the name of the script the window writes, analysis.py to start with (analysis1.py, analysis2.py and so on if that file is there already; the page warns you only if you type the name of a file that exists). For a comparison the folder is oceanval_simulation_comparison, and a comparison already there has to be ticked to be replaced in the same way, and the script is simulation_comparison.py, numbered in the same way.
  7. Run the analysis: the window writes the oceanval.analyze() call into a script, analysis.py unless you choose another name, runs it, and links to the report once it is built. While it runs, a grid has a row for each variable and a column for each analysis chosen for at least one of them (Climatology, Phenology, Long-term series, Seasonal cycles, Map changes, Transects): a hollow circle for what is still to do, a turning circle for what is being worked out now, a tick once it is, and a dash for an analysis that variable does not have. The Time column counts up while a variable is worked out and keeps how long it took, Time elapsed under the grid is how long the run has gone on for, and the Report column ticks as each variable’s page is added, the tick opening that page (in a narrow window the Report column is left out and the analyses’ names are turned on their side). Each variable’s page is built as soon as the variable is worked out, and the window links to this interim analysis report from the first variable on, saying how many of the variables are in it. The netCDF fields it worked out are kept beside the report, in oceanval_analysis/results. Save Python script to run later, to the right of it, writes the same script but does not run it: the window says where it is, and the command to run it in a terminal (python analysis.py), when you want to.

With raw FVCOM output, every analysis can be chosen, at the surface, the bottom or through the water column, whose cell thickness is not asked for, nor that of a transect’s section: it is worked out from the sigma levels, h and zeta, and a note above the analyses says so. The maps are drawn on the FVCOM mesh itself, and the spatial means are weighted by the areas of its cells.

Comparing simulations

Compare simulations does everything Analyze does for two to five simulations, and shows them side by side in one HTML report: the maps are a panel for each simulation on one colour scale, and the time series have a colour for each simulation. It takes you through these pages, each with Back:

  1. Which simulations do you want to compare? A Name for each (which is how the report calls it), the Directory its output is in and how many directories down its files are (typed, or picked from 0 to 5 in the box’s list, or filled in for you when the folders are recognised, as above), with the same live check of the files as for a validation. Add up to five. Where the comparison is saved is asked last, on the final page.
  2. What variables do you want to compare? A row for each variable, with Environmental variable for it and, in a column for each simulation, the model variable holding it there, which can be called something different in each.
  3. Do the units match up? Only if a variable is not in the units the first simulation gives it in: the first simulation’s units are the comparison’s, and every other simulation is converted into them, as a validation converts the observations into the model’s units. There is a page for each simulation that needs one, with a row for each variable: its units in the first simulation and in this one, and Multiply by and Add (each value becomes value × Multiply by + Add as it is read, so every analysis is of the converted values). OceanVal fills in the conversions it can work out in red and bold; leave both boxes empty when the units are the same but written another way. Tick that you are happy with the units on each page to carry on.
  4. The files of each simulation and their dates. If the times of some look like the end of each mean’s period, the page first asks whether to shift them back a day. The simulations are compared over the years they all have.
  5. Do you need to unify the model grids? You must answer. With Yes, choose either a lon/lat box and a resolution (the simulations are put on that grid with nctoolkit’s to_latlon) or a baseline simulation, whose grid the others are regridded to with regrid. Choose the regridding method too (bilinear, nearest neighbour, distance-weighted or conservative; bilinear if you do not). The page shows a map of each simulation’s first variable (at the simulation’s second time step, if it has one), and Generate unified grid previews the cells they all have a value in on the grid you chose; it is only a preview, and Continue does not wait for it. Either way, a cell with no value in any one simulation is made missing in all of them, so that every simulation is compared over exactly the same cells; the page says so.
  6. Do you want to mask part of the domain? No to start. With Yes, give a netCDF file with a single variable and a single time step, 1 in the cells you want and 0 or missing elsewhere. The file is checked as you type its path and drawn on a map, with the number of cells that will be kept. Every simulation is regridded to the file’s grid using nearest neighbour (after the grids are unified, if you did that), and only the cells of 1 are kept.
  7. The analyses. The same six boxes as Analyze, worked out for every simulation over years all of them have, then, as for Analyze, a second page for the cores, the missing values and the figure code.
  8. Run the comparison: the window writes the oceanval.compare_simulations() call into a script, simulation_comparison.py unless you choose another name, runs it, and links to the report once it is built, and to the interim report from the first variable on, as for an analysis. The same grid of the variables and their analyses shows how far it has got: each analysis is worked out in each simulation in turn, so between them its cell shows how many simulations have it, such as 1/3, and it is ticked once all have. Save Python script to run later writes the script without running it, as for an analysis.

On a remote machine

If oceanval cannot open a browser for you, it prints a link to open. Over SSH it never opens a browser on the remote machine, even when X11 forwarding is on (as in MobaXterm); oceanval --no-browser does the same anywhere, and OCEANVAL_BROWSER=1 opens one over SSH anyway. VS Code forwards its port for you. Over plain SSH, for example from a Windows terminal, it prints the command that forwards the port, such as ssh -L 8765:127.0.0.1:8765 you@server: run it in a new terminal on your own computer (PowerShell on Windows 10 or later has ssh), leave it open, and open the link in your browser. When it prints that command, oceanval uses port 8765 if it is free, so the command is the same every time; choose another port with --port. When it opens the browser itself, as in VS Code, it uses any free port. The printed login is a guess: use the one you normally connect with. The run carries on if you close the page, and you can come back to it with the same link.

Keeping the data downloaded

The built-in observational datasets are downloaded every time a matchup needs them, and their servers can be slow or out of reach. To keep what is downloaded for later matchups, open Preferences (the cog beside the OceanVal name) and give a folder for the data store. The folder must already exist: OceanVal keeps everything in an oceanval_datastore folder it makes inside it, and never writes or removes anything outside that. Choose a disk with a reasonable amount of free space, as the store grows as more data is kept in it and can come to several GB. Leave the folder empty to keep nothing.

Once the folder is saved, Preferences shows where the store is, how much space is free on its disk and the size of the data store. Run a check on the data store looks for data held twice, files that are missing or not the size they were, and anything in the store that is not OceanVal’s built-in data (files of yours, for one), and says what it finds. It only looks: nothing is changed, removed or fixed.

Choose how matchups use it:

  • Always use data from your data store, if available: what is in the store is used, and only what is not is downloaded, and kept.
  • Only use the data store when download fails: everything is downloaded each time, as without a store, and kept, replacing the copy in the store. The copy is used only for what cannot be downloaded, and the run says so. A server that is slow, rather than one that fails, is waited for.

Only OceanVal’s own datasets are kept (WOA23, OC-CCI, NSBC, COBE2, GLODAP and ICES), never data of yours. What OceanVal downloads is the area and years a matchup needs, so the store keeps track of them: gridded data is kept for the model’s area, rounded out to whole degrees (or the whole globe, for a model covering 90% of it), and ICES data a year at a time for the area asked for. A later matchup whose area and years are inside what is kept takes it from the store; a wider area is downloaded again, and replaces what was kept with data covering both. Something downloaded earlier in the same run is never downloaded again, so the ICES bottle data every ICES nutrient comes from is downloaded once. What is kept is used however old it is, and the run says when it was downloaded; this year’s COBE2 data, still being added to, is not kept. The setting is used by every matchup, including those run from Python; oceanval.matchup(..., data_store=False) leaves it out for one run.

Running the output from Python

The window does nothing you could not do in Python. It writes the matchup script first, to matchup.py unless you choose another name, and then runs it. The script holds your own data, every recipe (those you did not tick are commented out), the conversions, the oceanval.matchup() call and, for a matchup and validate run, the oceanval.validate() call, so you can read it, edit it and run it again later with python matchup.py.
