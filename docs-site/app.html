The OceanVal app

Validate or analyse a simulation from a browser window, with no Python.

The OceanVal app lets you validate a simulation without writing any Python. Run oceanval in a terminal and a page opens in your web browser that takes you from a folder of model output to a validation report: you choose what to do, point it at your simulation, choose the observations to validate against, check the units, and watch the run. The first page offers Analyze and Validate: Validate leads to the validation choices, and Analyze looks at a simulation on its own (see below).

Start it

oceanval only runs from a conda environment that has OceanVal installed (see Installing), as it needs the R packages, cdo and nco that conda provides. In a terminal, activate that environment, then run oceanval in the directory to work in:

bash 
conda activate foo
oceanval

Replace foo with the name of your own environment. If the command is not found, the environment is not active, or OceanVal is not installed in it. OceanVal and python -m oceanval do the same. Matchups, scripts and reports are written in that directory unless you choose another, so make a new directory for each simulation.

Demo

Analyzing a simulation

Analyze works out the climatology, the phenology, time series and transects of a simulation’s variables, with no observations, and builds an HTML report of them, laid out like a validation report. It takes you through these pages, each with Back, which keeps what you entered:

  1. Simulation: where the model output is, as for a validation, but with no domain to choose. The analysis is saved in a folder called oceanval_analysis in the directory you choose, replacing any analysis there.
  2. What variables do you want to analyse? A row for each variable, with Your name for it and the Model name holding it, typed or ticked in the pop-out of the model’s variables under the box; ticking several sums them. The arrow at the right-hand end of Your name lists the names OceanVal knows from validation (Temperature, Salinity, Chlorophyll and so on): choosing one fills in the Model name as the matchups would find it (shown in red and bold until you change it), if your model has a variable for it. Nothing else is filled in for you: the rows start empty.
  3. The files holding each variable, their time resolution and their dates. OceanVal reads the date of every file and says whether any are missing; Show the months shows which. If the model’s time means look dated at the end of the period each covers, the page first asks whether to shift every time back a day.
  4. What do you want to work out? Six boxes, Climatology, Phenology, Long-term time series, Seasonal time series, Map temporal changes and Transects, each opening a large pop-out with a row for each variable, and Cancel and Confirm at the bottom. What has to be given is marked Required, in red: Confirm stays greyed out until at least one variable has Surface, Bottom, Water column or more than one ticked (or, for the phenology, is ticked), and each ticked variable needs its years. Once an analysis has been confirmed, a Remove this analysis button appears in its pop-out to leave it out again. The climatology is the mean of each month of the year, and the annual mean, over the years from Start to End, at the Surface, at the Bottom (the deepest value that is not missing) and/or through the Water column, as its vertical mean or its depth integral, which needs the cell thickness (the name of its variable, a file, or z_level). The phenology is the day of the seasonal peak at the surface, from a daily climatology, so it is offered only for daily output. The two time series are the mean of each year, and of each month, over the model’s domain, each region you choose and each station (a name, longitude and latitude, in a table in their pop-outs; the nearest model cell is used). Once one is chosen, a card sets the regions and area they share: no regional summaries, the northwest European Shelf, global, or your own .nc file, and a lon/lat box. Map temporal changes maps how a variable changes between a historical period and one or two future periods: for each variable ticked, give the first and last years of the Historical period and of Future 1 (both required) and, if you like, Future 2, tick Surface, Bottom and/or Water column as for the climatology, and choose, in a row below, Plot (Historical + Future (absolute values), Historical + Future (absolute values) + Changes or Historical + Changes) and Change (absolute or percentage); neither is chosen to start with. Transects are the model’s values along straight lines: tick each variable you want transects of, and add as many transects as you like to each, on its own. A transect is a card with the longitude and latitude of its Start and End (it must run north–south, with the same longitude at both ends, or east–west, with the same latitude) in one line, and, below them, a Surface and a Vertical part, each with a Climatology (at the surface, the monthly climatology along the line; in the vertical, a section of the annual mean through the water column, which asks whether the simulation is z-level or where its cell thickness is) and its Changes, a drop-down of Absolute (the linear trend per year), Absolute change (the last year minus the first) and Percentage change, at the surface or at each depth of the section, which are not offered for a variable with only one year of output (the absolute trend needs three). Each has its own required Start year and End year, and a Rolling mean (years) box to the right of those of the changes, 1 to start with (none), smooths the annual means with nctoolkit’s rolling_mean before the trend is worked out. Nothing is ticked or filled in to start with, and each variable’s years of output are shown beside it as a hint. Every start and end year box also has an arrow at its right-hand end (or press the down arrow in the box) that lists all the years of that variable’s output to pick from; a year can still be typed. The Long-term time series pop-out has two more columns after Water column: Rolling mean (years), 1 to start with (none), which replaces each year’s annual mean by the mean of that year and the ones before it, and Show as: Absolute value (the annual means, to start with), Absolute change or Percentage change, each year’s change from the first year with a value. Below the boxes you must say how many cores OceanVal may use, which has no default, and what to treat as missing values; OceanVal looks at the surface of the first variable at the first time step of up to ten of its files, and if a value is the same in a good many cells of every file (as land is) it fills it in, in amber, and asks you to check it; otherwise, as for validation, a NEMO-ERSEM simulation is recognised and zeros are assumed, marked as such. Anything you type is kept. You must also answer Do you want the report to contain code to reproduce figures?, Yes or No, with neither chosen to start with: with Yes, each figure in the report has a Copy code to reproduce figure button at its top right, which copies the Python code that draws it from the analysis’s saved results, to change and run in the conda environment OceanVal ran in.
  5. Run the analysis: the window writes the oceanval.analyze() call into a script, analysis.py unless you choose another name, runs it, and links to the report once it is built. The netCDF fields it worked out are kept beside the report, in oceanval_analysis/results.

On a remote machine

If oceanval cannot open a browser for you, it prints a link to open. VS Code forwards its port for you. Over plain SSH, for example from a Windows terminal, it prints the command that forwards the port, such as ssh -L 8765:127.0.0.1:8765 you@server: run it in a new terminal on your own computer (PowerShell on Windows 10 or later has ssh), leave it open, and open the link in your browser. When it prints that command, oceanval uses port 8765 if it is free, so the command is the same every time; choose another port with --port. When it opens the browser itself, as in VS Code, it uses any free port. The printed login is a guess: use the one you normally connect with. The run carries on if you close the page, and you can come back to it with the same link.

Keeping the data downloaded

The built-in observational datasets are downloaded every time a matchup needs them, and their servers can be slow or out of reach. To keep what is downloaded for later matchups, open Preferences (the cog beside the OceanVal name) and give a folder for the data store. The folder must already exist: OceanVal keeps everything in an oceanval_datastore folder it makes inside it, and never writes or removes anything outside that. Choose a disk with a reasonable amount of free space, as the store grows as more data is kept in it and can come to several GB. Leave the folder empty to keep nothing.

Once the folder is saved, Preferences shows where the store is, how much space is free on its disk and the size of the data store. Run a check on the data store looks for data held twice, files that are missing or not the size they were, and anything in the store that is not OceanVal’s built-in data (files of yours, for one), and says what it finds. It only looks: nothing is changed, removed or fixed.

Choose how matchups use it:

  • Always use data from your data store, if available: what is in the store is used, and only what is not is downloaded, and kept.
  • Only use the data store when download fails: everything is downloaded each time, as without a store, and kept, replacing the copy in the store. The copy is used only for what cannot be downloaded, and the run says so. A server that is slow, rather than one that fails, is waited for.

Only OceanVal’s own datasets are kept (WOA23, OC-CCI, NSBC, COBE2, GLODAP and ICES), never data of yours. What OceanVal downloads is the area and years a matchup needs, so the store keeps track of them: gridded data is kept for the model’s area, rounded out to whole degrees (or the whole globe, for a model covering 90% of it), and ICES data a year at a time for the area asked for. A later matchup whose area and years are inside what is kept takes it from the store; a wider area is downloaded again, and replaces what was kept with data covering both. Something downloaded earlier in the same run is never downloaded again, so the ICES bottle data every ICES nutrient comes from is downloaded once. What is kept is used however old it is, and the run says when it was downloaded; this year’s COBE2 data, still being added to, is not kept. The setting is used by every matchup, including those run from Python; oceanval.matchup(..., data_store=False) leaves it out for one run.

Running the output from Python

The window does nothing you could not do in Python. It writes the matchup script first, to matchup.py unless you choose another name, and then runs it. The script holds your own data, every recipe (those you did not tick are commented out), the conversions, the oceanval.matchup() call and, for a matchup and validate run, the oceanval.validate() call, so you can read it, edit it and run it again later with python matchup.py.
